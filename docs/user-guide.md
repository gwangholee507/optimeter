# 사용자 가이드

이 문서는 **Optimeter**(컴파일러 최적화 옵션 비교기)를 실제로 써보고 싶은 사람을 위한 안내서입니다.
코드 구조가 아니라 "어떻게 실행하고, 화면을 어떻게 읽으면 되는지"에 초점을 맞췄습니다.
(개발자용 코드 설명은 [backend.md](./backend.md), [frontend.md](./frontend.md) 참고)

---

## 1. 이 앱은 무엇을 하나요?

C, C++, Rust 코드를 입력하면, 선택한 컴파일러(C는 **Clang**/**GNU GCC**, C++은 **Clang++**/**GNU G++**,
Rust는 **rustc**)가 최적화 수준(C/C++은 `-O0`, `-O1`, `-O2`, `-O3`, Rust는 `opt-level` `0`, `1`, `2`, `3`, `s`, `z`)을
다르게 적용했을 때
- 생성되는 **어셈블리 코드**가 어떻게 달라지는지
- **컴파일된 코드 크기**가 얼마나 줄어드는지
- **컴파일 시간**이 얼마나 걸리는지
- (옵션) **실제 실행 시간**이 얼마나 빨라지는지

를 레벨별 열(column)로 나란히 보여줍니다. "컴파일러 최적화가 대체 뭘 하는 거지?", "clang이랑 gcc는
같은 코드를 어떻게 다르게 최적화하지?"를 눈으로 직접 확인해보기 위한 학습용 도구입니다.

## 2. 처음 실행하기

### 준비물

macOS, Linux, Windows에서 실행할 수 있습니다.

- `clang` — macOS는 Xcode Command Line Tools(`xcode-select --install`)에 포함되어 있고,
  Ubuntu/Debian은 `sudo apt-get install clang`으로 설치합니다. Windows는 바로 아래
  [Windows에서 컴파일러 준비하기](#windows에서-컴파일러-준비하기)를 참고하세요.
- JDK 17 이상. Maven과 Node.js는 따로 설치하지 않아도 됩니다.
- (선택) GNU GCC — 설치하면 컴파일러 드롭다운에 "GNU GCC"도 뜨고 선택할 수
  있습니다. 설치 안 해도 앱은 정상 동작하며, 이 경우 드롭다운에는 Clang만 나옵니다.
  macOS는 `brew install gcc`, Ubuntu/Debian은 `sudo apt-get install gcc`로 설치합니다.
  > ⚠ macOS 기본 `gcc` 명령은 사실 Apple clang의 별칭이라 진짜 GCC가 아닙니다. 서버가 자동으로
  > 이를 걸러내므로, macOS에서 진짜 GCC와 비교하려면 반드시 Homebrew로 설치해야 합니다.
- (선택) C++ 컴파일러 — 설치하면 **언어** 드롭다운에서 C++을 고를 수 있습니다.
  - `clang++`: clang과 함께 설치됩니다 (macOS의 Xcode Command Line Tools, Ubuntu의 `clang` 패키지).
  - `g++`: macOS는 `brew install gcc`에 `g++-16` 같은 이름으로 함께 들어 있고, Ubuntu/Debian은
    `sudo apt-get install g++`로 설치합니다. macOS 기본 `g++`도 clang의 별칭이라 gcc와 같은 이유로 걸러집니다.
- (선택) Rust 컴파일러 `rustc` — 설치하면 **언어** 드롭다운에서 Rust를 고를 수 있습니다.
  [rustup](https://rustup.rs/)으로 설치하는 것을 권장합니다. 세 OS 모두 같은 방법이고, 기본 설치 위치(`~/.cargo/bin`)는
  PATH에 없어도 서버가 찾습니다. cargo를 쓰지 않으므로 **파일 하나와 표준 라이브러리만** 컴파일할 수 있습니다
  (`rand` 같은 외부 크레이트는 쓸 수 없습니다). Windows에서 실행 시간까지 재려면 링커가 더 필요할 수 있으니
  [아래](#windows에서-컴파일러-준비하기)를 참고하세요.

준비물이 설치되어 있는지 확인하려면:
```bash
clang --version
java -version
gcc-16 --version   # macOS에서 brew install gcc로 설치한 경우 (버전 번호는 설치 시점에 따라 다를 수 있음)
gcc --version      # Linux/Windows에서 GCC를 설치한 경우
clang++ --version  # C++ (clang)
g++ --version      # C++ (GCC, macOS에서는 g++-16 처럼 버전이 붙은 이름)
rustc --version    # Rust
```

### Windows에서 컴파일러 준비하기

Windows에는 C 컴파일러가 기본으로 들어 있지 않아서 직접 설치해야 합니다. 가장 간단한 방법은
[MSYS2](https://www.msys2.org/)입니다.

1. MSYS2를 기본 위치(`C:\msys64`)에 설치합니다.
2. 시작 메뉴에서 **MSYS2 UCRT64** 터미널을 열고 컴파일러를 설치합니다.
   ```bash
   pacman -S mingw-w64-ucrt-x86_64-clang mingw-w64-ucrt-x86_64-gcc
   ```
3. 끝입니다. 서버가 시작할 때 `C:\msys64\ucrt64\bin`을 알아서 확인하므로 **PATH를 따로
   설정하지 않아도 됩니다.** 위 두 패키지에는 C++ 컴파일러(`clang++`, `g++`)도 들어 있어서 C++도 바로 쓸 수 있습니다.

다른 방법으로 설치한 경우:

- **PATH에 `clang`/`gcc`(C++은 `clang++`/`g++`)가 있으면** 그것을 먼저 사용합니다 (WinLibs 등 다른 MinGW-w64 배포판도 이 방식으로 동작).
- **LLVM 공식 설치 프로그램**으로 설치한 clang/clang++(`C:\Program Files\LLVM`)도 자동으로 찾습니다. 다만 이 clang은
  C/C++ 표준 헤더(`stdio.h`, `vector` 등)와 링커를 Visual Studio에서 가져다 쓰기 때문에, **Visual Studio Build Tools의
  "C++를 사용한 데스크톱 개발"** 이 함께 설치되어 있어야 `#include`가 있는 코드와 실행 시간 측정이 동작합니다.
- **그 밖의 위치**에 설치했다면 환경 변수로 실행 파일 경로를 직접 알려줄 수 있습니다 (macOS/Linux도 동일).
  ```powershell
  $env:OPTVIS_GCC = "D:\tools\mingw64\bin\gcc.exe"     # clang은 OPTVIS_CLANG
  $env:OPTVIS_GXX = "D:\tools\mingw64\bin\g++.exe"     # clang++은 OPTVIS_CLANGXX
  $env:OPTVIS_RUSTC = "D:\tools\rust\bin\rustc.exe"    # rustc
  .\mvnw.cmd spring-boot:run
  ```
- **Rust**는 rustup의 기본 설치 위치(`%USERPROFILE%\.cargo\bin`)와 MSYS2 UCRT64(`C:\msys64\ucrt64\bin`)를 자동으로 찾습니다.
  설치 방법에 따라 실행 시간 측정에 필요한 것이 다릅니다.

  | 설치 방법 | 어셈블리·크기 비교 | 실행 시간 측정 |
  |---|---|---|
  | [rustup](https://rustup.rs/) (권장) | 혼자 됨 | Visual Studio Build Tools의 **"C++를 사용한 데스크톱 개발"** 이 필요 (링커 `link.exe`) |
  | MSYS2: UCRT64 터미널에서 `pacman -S mingw-w64-ucrt-x86_64-rust` | 혼자 됨 | 혼자 됨 (MSYS2의 링커를 함께 설치함) |

  링커가 없어도 앱은 동작하고, 실행 시간 자리에만 `⏱ 실행 불가`가 뜹니다. 둘 다 설치되어 있으면 rustup 쪽을 씁니다.

서버가 어떤 컴파일러를 찾았는지는 백엔드를 실행할 때 뜨는 로그에서 확인할 수 있습니다.
```
컴파일러 'clang'(Clang (LLVM)) → C:\msys64\ucrt64\bin\clang.exe
컴파일러 'gcc'(GNU GCC) → C:\msys64\ucrt64\bin\gcc.exe
컴파일러 'clangxx'(Clang++ (LLVM)) → C:\msys64\ucrt64\bin\clang++.exe
컴파일러 'gxx'(GNU G++) → C:\msys64\ucrt64\bin\g++.exe
컴파일러 'rustc'(rustc (LLVM)) → C:\Users\me\.cargo\bin\rustc.exe
```

> Windows에서 만든 어셈블리는 macOS/Linux와 모양이 다릅니다(섹션 이름, 심볼 표기, 호출 규약 등).
> 운영체제마다 실행 파일 형식과 함수 호출 규칙이 다르기 때문이며, 정상입니다.

### 실행하기

**방법 1 — jar 파일 내려받아 실행 (가장 간단)**

[Releases](https://github.com/gwangholee507/optimeter/releases) 페이지에서 `optimeter-<버전>.jar`를 내려받고, 터미널에서 실행합니다.
```bash
java -jar optimeter-<버전>.jar
```

**방법 2 — 소스에서 바로 실행**

저장소를 내려받았다면 `backend` 폴더에서 명령 하나로 실행할 수 있습니다.
```bash
cd backend
./mvnw -Pbundle spring-boot:run        # Windows(PowerShell/cmd): .\mvnw.cmd -Pbundle spring-boot:run
```
(처음 실행할 때는 Maven, 라이브러리, 화면 빌드용 Node.js를 내려받느라 몇 분 걸릴 수 있습니다.)

어느 방법이든 `Tomcat started on port 8080` 같은 로그가 뜨면 준비 완료입니다.
브라우저에서 **`http://localhost:8080`** 을 열면 됩니다. 끝낼 때는 터미널에서 `Ctrl+C`를 누릅니다.

> 화면과 서버가 프로그램 하나로 합쳐져 있어서 따로 띄울 것이 없습니다.
> 코드를 고치면서 개발하려는 경우의 실행 방법은 [README의 "개발할 때"](../README.md#개발할-때)를 참고하세요.

### 포트를 바꾸거나 다른 기기에서 접속하려면

- **포트 변경**: 8080번을 이미 다른 프로그램이 쓰고 있다면 실행 명령 끝에 `--server.port=9090`을 붙입니다.
  (방법 2는 `./mvnw -Pbundle spring-boot:run -Dspring-boot.run.arguments=--server.port=9090`)
- **다른 기기에서 접속**: 기본적으로는 **이 프로그램을 실행한 PC에서만** 접속할 수 있습니다. 이 프로그램은 받은
  코드를 컴파일하고 (옵션으로) 실행까지 하기 때문에, 같은 Wi-Fi의 다른 사람이 접속할 수 있으면 그 사람이
  내 PC에서 임의의 프로그램을 실행할 수 있게 됩니다. 그래도 필요하다면 믿을 수 있는 네트워크에서만
  `--server.address=0.0.0.0`을 붙여 실행하세요. 다른 기기에서는 `http://192.168.0.5:8080`처럼 **IP 주소**로 접속합니다.
  `http://my-mac.local:8080`처럼 컴퓨터 이름으로 접속하면 "이 주소로는 접속할 수 없습니다"라고 나옵니다.
  다른 웹사이트가 이름을 속여 이 프로그램을 호출하는 것을 막기 위해 `localhost`와 IP 주소만 받기 때문입니다.
  이름으로 접속해야 한다면 `--optimeter.allowed-hosts=my-mac.local`을 함께 붙여 실행하세요 (여러 개는 쉼표로 구분).

## 3. 화면 사용법

### 3.1 코드 입력
1. **언어** 드롭다운에서 C, C++, Rust 중 하나를 고릅니다. 언어를 바꾸면 그 언어의 예시 코드가 들어갑니다.
   서버에 그 언어의 컴파일러가 하나도 없으면 회색으로 비활성화되어 선택할 수 없습니다.
2. 화면 위쪽의 검은 텍스트 박스에 코드를 입력합니다. (처음 접속하면 C 예시 코드가 미리 채워져 있습니다)
   - 박스 왼쪽에 줄 번호가 붙어 있습니다. 최적화 기록의 `8행`이나 컴파일 에러의 `input.c:8:5`가 어느 줄인지 여기서 찾으면 됩니다.
   - 긴 줄은 다음 줄로 접히지 않고 박스 안에서 가로로 스크롤됩니다 (줄 번호와 줄이 어긋나지 않게 하려는 것입니다).
     박스 오른쪽 아래 모서리를 끌면 높이를 늘릴 수 있습니다.
   - 고치던 코드는 언어별로 따로 기억합니다. C 코드를 고치다가 C++로 갔다 와도 고치던 C 코드가 그대로 남아 있습니다.
     (페이지를 새로고침하면 사라집니다)
   - **예제로 되돌리기** 버튼을 누르면 지금 언어의 예시 코드로 돌아갑니다.
3. `main()` 함수는 없어도 됩니다 — 이 앱은 실행 파일이 아니라 **오브젝트 파일(.o)** 을 기준으로
   크기를 비교하기 때문에, `square(int x)`처럼 함수만 있어도 됩니다. Rust는 조금 다릅니다 (3.5절 참고).
4. **컴파일러** 드롭다운에서 사용할 컴파일러를 고릅니다. 지금 언어의 컴파일러만 나오고, 서버에 설치되지 않은
   컴파일러는 회색으로 비활성화되어 선택할 수 없습니다. 컴파일러를 바꿔도 입력한 코드는 그대로입니다.
5. 실제 실행 시간까지 보고 싶으면 **실행 시간 측정** 체크박스를 켭니다. (자세한 내용은 3.4절 참고)
6. **비교하기** 버튼을 클릭합니다.

### 3.2 결과 읽는 법

버튼을 누르면 아래에 레벨별 박스가 나란히 나타납니다. C/C++은 `-O0`, `-O1`, `-O2`, `-O3` 네 개, Rust는
`opt-level=0`, `1`, `2`, `3`, `s`, `z` 여섯 개입니다. 아래 설명은 C/C++ 기준이며, Rust에서는 첫 번째 레벨인
`opt-level=0`이 `-O0` 역할을 합니다. 박스 제목과 비교 기준 버튼에도 `opt-level=0`처럼 표시됩니다.

```
비교 기준 ⓘ  [-O0] -O1  -O2  -O3                 ☑ 지시어 숨기기 ⓘ
┌─────────────┬─────────────┬─────────────┬─────────────┐
│ -O0 ⓘ 기준  │ -O1 ⓘ       │ -O2 ⓘ       │ -O3 ⓘ       │
│ 712B · 52ms │ 648B · 38ms │ 648B · 35ms │ 648B · 35ms │
│             │ (+18/-35)   │ (+18/-35)   │ (+18/-35)   │
├─────────────┼─────────────┼─────────────┼─────────────┤
│ ▾ 최적화 기록 │ ▾ 최적화 기록 │ ▾ 최적화 기록 │ ▾ 최적화 기록 │
│  (기록 없음) │ 적용 2 놓침 1│ 적용 2 놓침 2│ 적용 2 놓침 2│
├─────────────┼─────────────┼─────────────┼─────────────┤
│ 어셈블리 코드 │ 어셈블리 코드 │ 어셈블리 코드 │ 어셈블리 코드 │
│  (기본 색상) │ (바뀐 줄은  │ (바뀐 줄은  │ (바뀐 줄은  │
│             │  초록색)    │  초록색)    │  초록색)    │
└─────────────┴─────────────┴─────────────┴─────────────┘
```

각 박스 안 요소들의 의미:

| 요소 | 의미 |
|---|---|
| **레벨 이름 옆 ⓘ 아이콘** | 마우스를 올리거나(또는 Tab 키로 포커스) 하면 그 최적화 레벨이 뭘 하는지 설명이 뜹니다. `clang -O0`~`-O3`가 뭔지 아직 익숙하지 않다면 여기부터 읽어보세요. |
| **크기 (예: 712B, 648B)** | 그 레벨로 컴파일했을 때의 오브젝트 파일 크기. 숫자가 작을수록 컴파일된 코드가 더 압축됐다는 뜻입니다. |
| **시간 (예: 52ms)** | 그 레벨로 컴파일하는 데 걸린 시간(어셈블리와 오브젝트 파일 생성 기준). 최적화를 많이 할수록 컴파일 자체는 더 오래 걸리는 경향이 있습니다. 컴퓨터를 켜고 처음 비교한 값에는 디스크를 읽는 시간이 섞여서 `-O0`만 유난히 길게 나올 수 있으니, 두 번째 비교의 값을 보세요. 레벨들을 동시에 컴파일하므로 CPU를 나눠 쓴 만큼 혼자 컴파일할 때보다 조금 길게 나올 수 있습니다. |
| **비교 기준 버튼** | 박스들 위에 있는 `-O0` `-O1` `-O2` `-O3` 버튼입니다. 누른 레벨이 아래 배지와 초록색 강조의 기준이 됩니다. 기본은 `-O0`이고, 다시 **비교하기**를 누르면 `-O0`으로 돌아갑니다. 컴파일에 실패한 레벨은 고를 수 없습니다. |
| **지시어 숨기기** | 비교 기준 버튼 줄의 오른쪽 끝(좁은 화면에서는 다음 줄의 오른쪽 끝)에 있는 체크박스로, 처음에는 켜져 있습니다. 어셈블러에게 주는 지시(`.cfi_startproc`, `.p2align`, `.section`처럼 `.`으로 시작하는 줄), 주석만 있는 줄, 그런 지시에서만 쓰는 내부 레이블(`.Lfunc_end0:`, `Lloh0:` 등), 디버그 정보와 예외 처리 표를 숨겨서 실제로 실행되는 명령어와 데이터(상수 문자열, 전역 변수의 값)만 보여줍니다. 초록색 강조와 배지도 남은 줄만으로 계산하므로, 의미 없는 줄 때문에 "바뀐 줄"이 부풀려지지 않습니다. 컴파일러가 내놓은 원본 그대로 보고 싶으면 끄면 됩니다. 다시 컴파일하지 않고 바로 바뀌며, 크기와 시간 숫자는 그대로입니다. |
| **기준 배지** | 지금 비교 기준인 박스의 레벨 이름 옆에 붙고, 그 박스는 테두리가 보라색으로 바뀝니다. |
| **(+18 / -35 vs -O0) 배지** | 비교 기준 레벨 대비 몇 줄이 새로 생기고(+) 몇 줄이 사라졌는지(-)를 나타내는 요약입니다. 기준 박스 자신에는 표시되지 않습니다. |
| **최적화 기록** | 컴파일러가 그 레벨에서 직접 남긴 기록입니다. 무슨 최적화를 했고(적용) 무엇을 하려다 못 했는지(놓침)를 소스 줄 번호와 함께 보여줍니다. C/C++에서만 나옵니다. 바로 아래 ["최적화 기록 읽는 법"](#최적화-기록-읽는-법) 참고. |
| **초록색으로 강조된 줄** | 기준 레벨의 어셈블리에는 없던, 이 레벨에서 새로 생기거나 바뀐 줄입니다. 최적화가 "구체적으로 어디를 바꿨는지" 여기서 확인할 수 있습니다. |
| **강조되지 않은 줄** | 기준 레벨에도 똑같이 존재하는 줄 — 이 레벨에서는 그대로 유지된 부분입니다. |
| **(줄이 너무 많아 비교 생략)** | 어셈블리가 너무 길어서(대략 1만 줄끼리 비교할 때) 바뀐 줄을 계산하지 않았다는 뜻입니다. 어셈블리는 그대로 볼 수 있고 강조만 없습니다. |

> **기준을 바꿔 보면 좋은 경우**: `-O0`과 비교하면 거의 모든 줄이 초록색이라 무엇이 중요한지 보기 어렵습니다.
> 기준을 `-O2`로 바꾸면 `-O3`가 `-O2`보다 **더** 한 일(예: 루프 벡터화)만 남아서 레벨 사이의 차이가 훨씬 잘 보입니다.

#### 최적화 기록 읽는 법

초록색 강조는 어셈블리의 **어디가** 바뀌었는지 보여주고, 최적화 기록은 컴파일러가 **무엇을 했는지**를 알려줍니다.
어셈블리 모양을 보고 추측한 것이 아니라 컴파일러가 컴파일하면서 직접 출력한 내용입니다
(clang의 `-Rpass`, GCC의 `-fopt-info`).

기록 한 건은 이렇게 생겼습니다.

```
적용  8행  함수 인라이닝
'square' inlined into 'sum_loop' with (cost=-30, threshold=337) at callsite sum_loop:3:18;
```

| 부분 | 의미 |
|---|---|
| **적용** (초록색) / **놓침** (노란색) | 적용은 컴파일러가 실제로 한 최적화, 놓침은 시도했지만 하지 못한 최적화입니다. 놓침은 "여기를 더 빠르게 만들 수 있었는데 못 했다"는 단서라서, 코드를 고칠 때 가장 쓸모 있는 줄입니다. |
| **8행** | 내가 입력한 소스 코드의 줄 번호입니다. 위 예에서는 8번째 줄의 `square(i)` 호출이 인라인됐다는 뜻입니다. 코드 입력 박스 왼쪽의 줄 번호와 같습니다. |
| **함수 인라이닝** | 최적화 종류입니다. 점선 밑줄이 있으면 마우스를 올렸을 때 그 최적화가 무엇인지 설명이 뜹니다. 앱이 아는 종류가 아니면 컴파일러가 붙인 이름(예: `early-ifcvt`)이 그대로 나오고, GCC의 일부 기록은 종류 없이 메시지만 나옵니다. |
| **아랫줄의 영어 문장** | 컴파일러가 출력한 원문입니다. `cost`와 `threshold`는 인라이닝 여부를 정한 점수와 기준값이고, GCC의 `square/1` 같은 숫자는 컴파일러 내부의 함수 번호입니다. |
| **×2** | 같은 줄에 같은 기록이 두 번 나왔다는 뜻입니다. 컴파일러가 같은 루프를 여러 번 다시 살펴볼 때 생깁니다. |

제목 줄(`▾ 최적화 기록  적용 2  놓침 1`)을 누르면 접을 수 있습니다. 레벨 사이의 차이는 건수만 봐도 드러납니다.
기본 예제를 GCC로 비교하면 `-O2`에는 `놓침 7행 루프 벡터화 — couldn't vectorize loop`가, `-O3`에는
`적용 7행 루프 벡터화 — loop vectorized using 16 byte vectors`가 나와서, `-O3`가 `-O2`보다 더 하는 일이 바로 보입니다
(메시지와 건수는 컴파일러 버전과 CPU에 따라 다릅니다).

알아둘 점:

- **`-O0`에는 보통 기록이 없습니다.** 최적화를 하지 않으니 남길 것도 없습니다.
- **Rust에는 최적화 기록이 나오지 않습니다.** 이유는 [rust.md](./rust.md)에 있습니다.
- **내 코드의 줄에 대한 기록만 보여줍니다.** `<vector>` 같은 헤더 안에서 일어난 최적화는 가리킬 내 코드의 줄이 없어서 뺍니다.
  C++에서 기록의 함수 이름은 `_ZNSt3__110accumulate...`처럼 맹글링된 채로 나옵니다.
- **레지스터 할당 통계처럼 최적화가 아닌 기록은 뺍니다.** 그래도 낯선 이름의 기록이 섞여 나올 수 있는데, 모르는 것은 넘어가도 됩니다.
- **한 레벨에 200건이 넘으면 앞쪽 줄부터 200건만 보여주고** 나머지는 몇 건을 생략했는지만 알려줍니다.
- 기록은 소스 줄 기준입니다. 어셈블리의 어느 줄이 그 최적화의 결과인지는 초록색 강조와 함께 직접 찾아봐야 합니다.

### 3.3 실전 예시로 읽어보기

기본으로 채워지는 예시 코드에는 `square(int x) { return x * x; }` 함수가 있습니다.

- **-O0**: `x`를 스택에 저장했다가 다시 읽어서 곱하는, 사람이 짠 코드와 거의 1:1로 대응하는 비효율적인 어셈블리가 나옵니다.
- **-O1부터**: `mul w0, w0, w0` 단 한 줄로 줄어듭니다. 스택에 저장하고 다시 읽는 불필요한 과정이 통째로 사라진 거죠.
  이 줄이 바로 초록색으로 강조되어 보이는 부분입니다.

`sum_loop`의 `-O1` 박스에 나오는 최적화 기록 `적용 8행 함수 인라이닝`은 루프 안의 `square(i)` 호출이 사라지고 곱셈이
루프 안으로 들어왔다는 뜻입니다. 어셈블리에서 `sum_loop` 안의 `bl _square`(함수 호출)가 없어진 것으로 확인할 수 있습니다.
같은 박스의 `적용 7행 루프 삭제`는 한 걸음 더 나간 결과입니다. clang은 0부터 n-1까지의 제곱의 합을 공식으로 바로 계산할 수 있다는 것을
알아내서 루프 자체를 지웁니다 (Apple clang 21 기준이며, 기록의 내용은 컴파일러 버전에 따라 다릅니다).

이런 식으로 "내가 짠 코드가 실제로 어떻게 최적화되는지"를 함수별로 비교해보면 좋습니다.
Rust 예제는 [3.5절의 "Rust 예제로 읽어보기"](#rust-예제로-읽어보기)에서 같은 방식으로 풀어 봅니다.

### 3.4 실행 시간 측정 (옵션)

**실행 시간 측정** 체크박스를 켜고 비교하면, 각 박스 메타 정보에 `⏱ 실행 3.42ms`처럼
실제로 실행해서 걸린 시간이 추가로 표시됩니다.

- 동작 방식: 서버가 최적화 레벨마다 실제로 **링크해서 실행 파일을 만들고, 5번 실행해서 그중
  가장 빠른 시간**을 채택합니다. 이 기능은 `main()` 함수가 있어야만 동작합니다.
  (실행 파일을 만들자마자 시간을 재지 않고 한 번 더 실행해 둡니다. 새 실행 파일을 처음 실행할 때 OS가 하는 검사를
  레벨끼리 동시에 끝내 두어서 결과가 빨리 나오게 하려는 것으로, 이 실행은 측정값에 들어가지 않습니다.)
- `main()`이 없는 코드(예: 기본 예시처럼 함수만 있는 코드)는 체크박스를 켜도 링크 자체가
  안 되므로, 컴파일/어셈블리 결과는 그대로 보이고 실행 시간 자리에는 회색 `⏱ 실행 불가`
  배지만 뜹니다. 오류가 아니라 정상적인 동작입니다.
- `main()`이 있는데도 `⏱ 실행 불가`가 뜬다면 배지에 마우스를 올려보세요. 링커나 컴파일러가 남긴 원본 메시지가
  함께 표시됩니다 (예: Windows에서 링커가 설치되어 있지 않은 경우, Rust에서 메서드 이름만 `main`이고 프로그램의 시작점이 없어서 E0601이 난 경우).
- 실행할 때 표준 입력은 비어 있어서, 입력을 읽는 코드는 입력 없이 바로 끝납니다.
- ⚠ 이 기능은 **서버가 사용자가 입력한 코드로 만들어진 프로그램을 그대로 실행**합니다.
  그래서 기본값이 꺼져 있고, 사용자가 직접 켜야만(옵트인) 동작합니다. 신뢰할 수 없는 코드를
  이 앱에 붙여넣고 실행 시간 측정을 켜지 마세요.
- 짧고 단순한 함수는 프로세스를 띄우고 종료하는 오버헤드가 실제 연산 시간보다 훨씬 커서,
  O0~O3 간 실행 시간 차이가 잘 안 보일 수 있습니다. 반복 횟수가 많은 루프가 있는 코드일수록
  최적화 레벨 간 차이가 더 뚜렷하게 나타납니다.

### 3.5 Rust 코드를 넣을 때

Rust는 코드에 `fn main`이 있는지에 따라 컴파일 방식이 달라집니다.

| 코드 | 컴파일 방식 | 어셈블리에 나오는 것 |
|---|---|---|
| `fn main`이 있음 | 프로그램 | `main`에서 실제로 쓰이는 코드 |
| `fn main`이 없음 | 라이브러리 | `pub` 함수와, 그 함수가 쓰는 코드 |

메서드 이름이나 모듈 안의 함수처럼 프로그램의 시작점이 아닌 `fn main`만 있어도 라이브러리로 컴파일합니다.

그래서 `pub` 없는 함수만 넣으면 어셈블리가 비고 노란색 안내 문구가 뜹니다. rustc는 아무도 쓰지 않는 비공개 함수를
만들지 않기 때문입니다. 함수를 `pub fn`으로 바꾸거나 `fn main`에서 호출해 보세요. 어떤 타입으로도 쓰이지 않은
제네릭 함수(`pub fn id<T>(x: T) -> T`)도 같은 이유로 나오지 않습니다. `#[inline]`이 붙은 함수는 `pub`이어도 쓰는 곳에서
만들어지므로 나오지 않습니다. `#[inline]`을 지우거나 `fn main`에서 호출해 보세요.

- 코드는 Rust **2021** 에디션으로 컴파일합니다. `cargo new`의 기본값인 2024 에디션 전용 문법(`if let ... && ...`)은 에러가 납니다.
- `opt-level=0`에서는 정수 오버플로 검사가 켜져 있고(`cargo build`와 같음) `1`부터는 꺼져 있습니다(`cargo build --release`와 같음).
  그래서 `opt-level=0`과 `1` 사이의 차이에는 최적화뿐 아니라 이 검사가 빠진 것도 섞여 있습니다.
- 같은 이유로 오버플로가 나는 코드는 `opt-level=0`에서만 패닉으로 멈춥니다. 도중에 끝난 시간은 다른 레벨과 비교할 수
  없으므로 그 레벨은 `⏱ 실행 불가`로 표시합니다.
- 어셈블리가 C보다 훨씬 길고 함수 이름이 `__RNvCs...5input8sum_loop`처럼 복잡합니다. 표준 라이브러리의 제네릭 코드가
  내 코드 안에 만들어지기 때문이고, 이름은 맹글링된 것입니다. 이름 속 숫자는 바로 뒤에 오는 이름의 글자 수라서,
  `5input`은 입력 파일 이름 `input`, `8sum_loop`는 함수 이름 `sum_loop`입니다.
- 실행 시간을 잴 때 컴파일러가 결과를 쓰지 않는 계산을 통째로 지워버릴 수 있습니다. `println!`으로 출력하거나
  `std::hint::black_box`로 값을 감싸면 막을 수 있습니다.
- 코드는 파일 하나만 쓸 수 있습니다. 파일 안에 쓴 `mod 이름 { ... }`은 되지만, 다른 파일을 불러오는 `mod 이름;`은
  파일을 찾지 못한다는 에러(E0583)가 납니다.

Rust 코드를 어떤 명령으로 컴파일하는지, 왜 그렇게 정했는지는 [rust.md](./rust.md)에 정리했습니다.

#### Rust 예제로 읽어보기

언어를 Rust로 바꾸면 이 예제 코드가 들어갑니다. `0`부터 `n-1`까지의 제곱을 더하는 함수를 반복자로 썼습니다.

```rust
fn square(x: i32) -> i32 {
    x * x
}

// fn main이 없으면 라이브러리로 컴파일되어 pub 함수만 어셈블리에 남습니다.
pub fn sum_loop(n: i32) -> i32 {
    (0..n).map(square).sum()
}
```

Apple Silicon Mac의 rustc 1.98.1에서 비교하면 이렇게 나옵니다. OS, CPU, rustc 버전이 다르면 명령어와 줄 수도 달라집니다.
어셈블리 줄 수는 화면의 기본값인 **지시어 숨기기**를 켠 상태와, 끈 상태(컴파일러가 내놓은 원본)를 함께 적었습니다.

| 레벨 | 어셈블리 (지시어 숨김 / 원본) | 오브젝트 파일 | 함수 수 |
|---|---:|---:|---:|
| `opt-level=0` | 286줄 / 549줄 | 7,216B | 15개 |
| `opt-level=1` | 93줄 / 116줄 | 1,568B | 4개 |
| `opt-level=2` | 18줄 / 26줄 | 592B | 1개 |
| `opt-level=3` | 18줄 / 26줄 | 592B | 1개 |
| `opt-level=s` | 47줄 / 67줄 | 1,360B | 3개 |
| `opt-level=z` | 29줄 / 52줄 | 1,352B | 4개 |

- **`opt-level=0`**: `map`, `fold`, `sum` 같은 표준 라이브러리의 반복자 함수가 내 코드 안에 하나씩 만들어져 함수가 15개나 됩니다.
  `square`를 보면 `x * x` 뒤에 결과가 `i32`를 넘는지 확인하고(`smull`로 한 번 더 곱해서 비교), 넘으면 `b.ne`로
  `panic_const_mul_overflow`를 부르는 곳으로 가는 분기가 붙어 있습니다. 이것이 오버플로 검사입니다.
- **`opt-level=1`**: 오버플로 검사가 사라지고 반복문도 없어집니다. 제곱의 합을 곱셈 몇 번으로 구하는 공식으로 바뀌었기 때문입니다.
  다만 `fold`, `sum` 같은 반복자 함수가 아직 따로 남아 있어 함수가 4개입니다.
- **`opt-level=2`**: 반복자 함수가 `sum_loop` 안으로 인라인되고 지워져서 `sum_loop` 하나만 남습니다. `(0..n).map(square).sum()`이라고
  써도 결과는 공식을 손으로 쓴 것과 다르지 않습니다. Rust가 말하는 "비용 없는 추상화"가 이것입니다.
- **`opt-level=3`**: `2`와 똑같습니다. 더 할 최적화가 남지 않은 코드에서는 흔한 일입니다.
- **`opt-level=s`, `z`**: 크기를 줄이는 레벨인데도 `2`보다 큽니다. 반복자 함수를 지우지 않고 따로 남겨 두었기 때문입니다.
  크기 레벨이 항상 가장 작은 것은 아니라는 걸 보여주는 예입니다.

비교 기준을 `opt-level=1`로 바꾸면 `2`가 `1`보다 무엇을 더 했는지만 남아서 인라인의 효과가 잘 보입니다.

#### Rust 실행 시간 재 보기

실행 시간은 `fn main`이 있는 코드만 잴 수 있습니다. 아래 코드를 넣고 **실행 시간 측정**을 켠 뒤 비교해 보세요.

```rust
use std::hint::black_box;

fn main() {
    let n = black_box(100_000_000u64);
    let mut total: u64 = 0;
    for i in 0..n {
        total = total.wrapping_add(i * i);
    }
    println!("{total}");
}
```

Apple Silicon Mac에서는 `opt-level=0`이 약 690ms, 나머지 레벨은 모두 4~5ms였습니다.

- `1`부터는 위 예제와 마찬가지로 1억 번 도는 반복문이 공식으로 바뀌어 사라집니다. 4~5ms는 계산 시간이 아니라 프로그램을 띄우고
  끝내는 데 드는 시간입니다.
- `black_box(n)`은 컴파일러가 `n`의 값을 모르게 합니다. 그냥 `100_000_000`을 쓰면 컴파일할 때 답을 미리 계산해 버릴 수 있습니다.
- `wrapping_add`는 합이 `u64`를 넘으면 값을 되감습니다. 그냥 `+`를 쓰면 합이 넘치는 순간 `opt-level=0`에서만 패닉이 납니다.

오버플로 패닉이 어떻게 보이는지는 이 코드로 확인할 수 있습니다.

```rust
use std::hint::black_box;

fn main() {
    let x: i32 = black_box(i32::MAX);
    println!("{}", x + 1);
}
```

`opt-level=0`에서는 `attempt to add with overflow` 패닉으로 멈추므로(종료 코드 101) `⏱ 실행 불가`가 뜹니다.
`1`부터는 값이 되감겨 `-2147483648`을 출력하고 정상으로 끝나므로 시간이 표시됩니다.

## 4. 컴파일이 실패했을 때

문법 오류가 있는 코드를 넣으면 각 박스 위쪽에 빨간색 **"컴파일 실패"** 배지가 뜨고,
본문에 컴파일러가 알려주는 원본 에러 메시지가 그대로 표시됩니다.

```
⚠ Clang (LLVM)가 이 코드를 컴파일하지 못했습니다
input.c:1:16: error: use of undeclared identifier 'retrun'; did you mean 'return'?
```

에러 메시지 형식은 `input.c:줄번호:칸번호: error: 설명` 입니다 (C++은 파일 이름이 `input.cpp`). 위 예시는
"1번째 줄, 16번째 칸에 `retrun`이라는 오타가 있다(→ `return`을 의도한 것 같다)"는 뜻입니다.
줄 번호는 코드 입력 박스 왼쪽에 표시된 번호와 같습니다. 이 정보를 참고해서 코드를 고친 뒤 다시 **비교하기**를 눌러보세요.

Rust는 형식이 조금 다릅니다. 첫 줄에 에러 번호와 설명이, `-->` 줄에 위치가 나오고, 그 아래에 문제의 코드와 고치는 방법(`help:`)을 보여줍니다.

```
⚠ rustc (LLVM)가 이 코드를 컴파일하지 못했습니다
error[E0425]: cannot find value `y` in this scope
 --> input.rs:2:9
  |
2 |     x * y
  |         ^
  |
help: a local variable with a similar name exists
  |
2 -     x * y
2 +     x * x
  |

error: aborting due to 1 previous error

For more information about this error, try `rustc --explain E0425`.
```

"2번째 줄, 9번째 칸의 `y`라는 값을 찾을 수 없고, 비슷한 이름의 `x`를 쓰려던 것 같다"는 뜻입니다. 마지막 줄처럼
`E0425` 같은 에러 번호의 자세한 설명은 터미널에서 `rustc --explain E0425`로 볼 수 있습니다.

### 코드 입력란을 비운 채로 제출하면?
화면 위쪽에 `⚠ 코드를 입력해주세요.` 라는 안내가 뜹니다. 코드를 입력하고 다시 시도하세요.

## 5. 자주 묻는 질문 (FAQ)

**Q. `-O2`와 `-O3`의 어셈블리가 똑같이 나올 때가 있어요. 버그인가요?**
아닙니다. 짧고 단순한 함수는 `-O2`에서 이미 최대로 최적화되어서, `-O3`이 추가로 적용하는
루프 벡터화 같은 고급 최적화가 적용될 여지가 없는 경우가 많습니다. 루프가 많거나 반복 연산이
있는 코드를 넣으면 `-O3`에서만 나타나는 차이를 볼 수 있습니다.

**Q. 크기가 0으로 나와요.**
`-O0`처럼 값이 정상적으로 나오는 레벨과 함께 0이 나온다면 버그일 수 있으니
[docs/backend.md](./backend.md)의 `CompilerService`를 참고해 오브젝트 파일 생성 과정을 확인해주세요.
정상적인 코드라면 보통 0이 나오지 않습니다.

**Q. "백엔드 서버에 연결할 수 없습니다"라고 떠요.**
서버가 꺼져 있다는 뜻입니다. 프로그램을 실행한 터미널이 닫혔거나 `Ctrl+C`로 종료되지 않았는지 확인하고,
[2. 처음 실행하기](#2-처음-실행하기)를 참고해 다시 실행하세요.

**Q. 실행했더니 "Port 8080 was already in use"라고 나와요.**
8080번 포트를 다른 프로그램(또는 이미 띄워둔 이 프로그램)이 쓰고 있습니다. 그 프로그램을 끄거나,
[포트를 바꿔서](#포트를-바꾸거나-다른-기기에서-접속하려면) 실행하세요.

**Q. 다른 컴퓨터에서도 똑같이 동작하나요?**
최소한 `clang`이 설치되어 있어야 하고, 운영체제(macOS/Linux/Windows)와 컴파일러 버전, CPU 아키텍처
(Intel/Apple Silicon 등)에 따라 생성되는 어셈블리가 달라집니다(예: x86과 ARM은 완전히 다른 명령어 집합을 씁니다).
같은 컴퓨터, 같은 컴파일러 버전으로 비교하는 것을 권장합니다.

**Q. 컴파일러 드롭다운에 "GNU GCC"가 안 보이거나 비활성화되어 있어요.**
서버가 실행 중인 컴퓨터에서 실제 GNU GCC를 찾지 못했다는 뜻입니다. macOS는
`brew install gcc`로 설치할 수 있습니다 (설치되는 실행 파일 이름이 `gcc-16`처럼 버전이 붙어서
`backend/src/main/resources/application.yml`의 `compiler.options` 후보 목록에 없는 새 버전이면
목록에 그 버전을 추가해야 인식됩니다). Ubuntu 등 Linux는 보통 `sudo apt-get install gcc`로 충분합니다.
Windows는 [Windows에서 컴파일러 준비하기](#windows에서-컴파일러-준비하기)를 참고하세요.
어느 OS든 설치는 했는데 인식이 안 된다면 `OPTVIS_GCC` 환경 변수에 실행 파일의 전체 경로를 넣고
백엔드를 다시 실행하면 됩니다.

**Q. 언어 드롭다운의 "C++"이 비활성화되어 있거나, 컴파일러 목록에 "GNU G++"가 안 보여요.**
위의 GCC와 같은 이유입니다. `clang++`이나 `g++`를 찾지 못했다는 뜻이니 [준비물](#준비물)을 참고해 설치하세요.
macOS의 `g++`는 Homebrew GCC에 `g++-16`처럼 버전이 붙어 들어 있습니다. 설치 위치를 직접 알려주려면
`OPTVIS_CLANGXX`(clang++), `OPTVIS_GXX`(g++) 환경 변수를 씁니다.

**Q. C++에서 `#include <vector>` 같은 표준 헤더를 쓰면 "file not found" 에러가 나요.**
주로 Windows에서 LLVM 공식 설치 프로그램의 clang++만 설치한 경우입니다. 이 clang++은 C++ 표준 라이브러리를
Visual Studio에서 가져다 쓰므로 **Visual Studio Build Tools의 "C++를 사용한 데스크톱 개발"** 을 설치하거나,
[MSYS2로 설치한 컴파일러](#windows에서-컴파일러-준비하기)를 쓰세요.

**Q. 언어 드롭다운의 "Rust"가 비활성화되어 있어요.**
서버가 `rustc`를 찾지 못했다는 뜻입니다. [rustup](https://rustup.rs/)으로 설치하고 서버를 다시 실행하세요.
다른 위치에 설치했다면 `OPTVIS_RUSTC` 환경 변수에 실행 파일의 전체 경로를 넣으면 됩니다.

**Q. Rust 코드를 넣었더니 어셈블리가 비어 있어요.**
`fn main`이 없고 어셈블리에 남는 `pub` 함수도 없는 코드입니다. [3.5절](#35-rust-코드를-넣을-때)을 참고해 `pub fn`으로 바꾸거나 `#[inline]`을 지우거나 `fn main`에서 호출해 보세요.

**Q. Rust에서 `use rand::Rng;` 같은 코드가 에러가 나요.**
이 앱은 cargo 없이 `rustc`로 파일 하나만 컴파일하므로 외부 크레이트를 쓸 수 없습니다. 표준 라이브러리(`std`)만 쓸 수 있습니다.

**Q. Rust 어셈블리가 너무 길고 함수 이름을 못 읽겠어요.**
`opt-level=0`에서는 표준 라이브러리의 반복자, `Vec`, `HashMap` 같은 코드가 인라인되지 않고 내 코드 안에 모두 만들어져서,
`HashMap`을 쓰는 짧은 프로그램도 만 줄이 넘습니다. **지시어 숨기기**를 켜 두면(기본값) 지시어와 예외 처리 표가 빠져서 30%쯤 줄어듭니다.
비교 기준을 `opt-level=1`이나 `2`로 바꾸면 레벨 사이의 차이가 훨씬 잘 보이고,
줄이 너무 많아 "(줄이 너무 많아 비교 생략)"이 뜰 때도 기준을 바꾸면 해결되는 경우가 많습니다.
함수 이름은 [3.5절](#35-rust-코드를-넣을-때)처럼 끝부분의 `8sum_loop` 같은 부분을 찾으면 됩니다.

**Q. Rust에서 크기를 줄이는 `opt-level=s`, `z`가 `opt-level=2`보다 커요. 버그인가요?**
아닙니다. 크기 레벨은 인라인을 덜 하는 대신 함수를 따로 남겨 두는데, 코드에 따라서는 인라인하고 지우는 쪽이 더 작아집니다.
기본 예제가 그런 경우이고, [3.5절의 예제 풀이](#rust-예제로-읽어보기)에서 자세히 볼 수 있습니다.

**Q. Rust에서 `opt-level=0`만 "실행 불가"가 떠요.**
대부분 정수 오버플로 때문입니다. 오버플로 검사는 `opt-level=0`에서만 켜져 있어서, 같은 코드가 `0`에서는 패닉으로 멈추고
`1`부터는 값이 조용히 되감긴 채 끝까지 돕니다. 배지에 마우스를 올리면 종료 코드(패닉은 101)를 볼 수 있습니다.
값이 넘치는 것이 의도라면 `wrapping_add`, `wrapping_mul`처럼 되감기를 명시하는 함수를 쓰세요.

**Q. Windows에서 Rust의 실행 시간만 "실행 불가"가 떠요.**
rustup으로 설치한 rustc는 실행 파일을 만들 때 Visual Studio의 링커를 씁니다. Visual Studio Build Tools의
"C++를 사용한 데스크톱 개발"을 설치하거나, MSYS2의 rustc를 쓰세요 ([Windows에서 컴파일러 준비하기](#windows에서-컴파일러-준비하기)).
배지에 마우스를 올리면 rustc가 남긴 링커 에러를 볼 수 있습니다.

**Q. "실행 시간"이 매번 값이 조금씩 달라져요.**
프로세스를 새로 띄워서 실행하는 방식이라 OS 스케줄링 등의 영향을 받습니다. 그래서 5번 실행해서
그중 최솟값을 보여주도록 되어 있지만(노이즈를 줄이기 위함), 그래도 완전히 통제된 벤치마크 환경은
아니라서 어느 정도의 변동은 정상입니다. 큰 흐름(예: O0이 O2/O3보다 눈에 띄게 느림)을 보는 용도로
쓰는 것을 권장합니다.

**Q. 아주 긴 코드나 무한 루프를 넣으면 어떻게 되나요?**
코드는 20,000자까지만 허용됩니다. 레벨 하나의 컴파일이 30초 안에 끝나지 않으면 서버가 자동으로 중단시킵니다.
다른 레벨이 성공했다면 그 레벨만 한 번 더 컴파일하고, 그래도 끝나지 않거나 모든 레벨이 시간을 넘기면 "컴파일 시간 초과" 에러를 표시합니다.
레벨은 동시에 컴파일하므로 모든 레벨이 시간을 넘기는 코드도 보통 약 30초 만에 결과가 나옵니다. 다만 서버를 켜고 그 컴파일러를
처음 쓰는 요청은 첫 레벨만 먼저 컴파일하고, 그 레벨도 시간을 넘기면 나머지를 한 레벨씩 기다리므로 C/C++은 약 2분, Rust는 약 3분이 걸립니다.
실행 시간 측정을 켰는데 `main()` 안에
무한 루프가 있다면, 5초 안에 끝나지 않는 실행을 마찬가지로 강제 종료하고 "실행 시간 초과"로 표시합니다.

**Q. 컴퓨터를 켜고 처음 비교하면 오래 걸려요.**
첫 컴파일은 컴파일러와 표준 라이브러리를 디스크에서 읽어야 해서 느립니다. 디스크가 느리면 짧은 코드도 10초 넘게, 긴 코드는 1분 넘게 걸릴 수 있습니다.
이때 시간 제한을 넘긴 레벨은 다른 레벨이 성공했다면 서버가 한 번 더 컴파일하고, 두 번째 비교부터는 빨라집니다.

**Q. 입력을 받는 프로그램은 어떻게 실행되나요?**
실행 시간을 잴 때는 표준 입력이 비어 있습니다. `scanf`나 `read_line`은 입력 없이 바로 끝나므로,
실제 입력이 필요한 계산이라면 값을 코드에 직접 넣어 주세요.

## 6. 알아두면 좋은 배경 지식

- `-O0`~`-O3`은 GCC/clang 계열 컴파일러(C++의 g++/clang++ 포함)의 **최적화 레벨** 옵션입니다. 숫자가 높을수록 더 적극적으로
  코드를 재구성하지만, 컴파일 시간이 늘어나고 디버깅은 더 어려워집니다.
- 실무에서는 개발 중에는 `-O0`(디버깅 쉬움), 배포할 때는 `-O2`(성능과 크기의 균형)를 주로 사용합니다.
- Rust는 `-C opt-level`로 같은 일을 합니다. `cargo build`는 `0`, `cargo build --release`는 `3`을 쓰고, `s`와 `z`는 코드 크기를 줄이는 레벨입니다.
  레벨별 의미는 [optimization-levels.md](./optimization-levels.md#rust의-opt-level), 이 앱이 Rust를 컴파일하는 방식은 [rust.md](./rust.md)에 있습니다.
- 이 앱에서 보여주는 "어셈블리"는 **AT&T 문법이 아니라 clang의 기본 출력(대상 아키텍처에 맞는 네이티브 어셈블리)**입니다.
  Apple Silicon(M1/M2/M3 등)에서 실행하면 ARM64 명령어가, Intel Mac에서 실행하면 x86-64 명령어가 나옵니다.
