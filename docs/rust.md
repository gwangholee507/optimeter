# Rust 지원

Optimeter가 Rust 코드를 어떻게 컴파일하고 보여주는지, C/C++과 무엇이 다른지, 왜 그렇게 정했는지를 한곳에 모은 문서입니다.
화면 사용법은 [사용자 가이드 3.5절](./user-guide.md#35-rust-코드를-넣을-때), 클래스 단위 설명은
[backend.md의 `RustcToolchain`](./backend.md#rustctoolchain)을 함께 보세요.

## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 컴파일러 | `rustc` (화면 이름 "rustc (LLVM)", API id `rustc`). cargo는 쓰지 않습니다 |
| 레벨 | `opt-level=0`, `1`, `2`, `3`, `s`, `z` 여섯 개 |
| 에디션 | 2021 고정 |
| 쓸 수 있는 코드 | 파일 하나와 표준 라이브러리(`std`). 파일 안에 쓴 `mod 이름 { ... }`은 됩니다 |
| 쓸 수 없는 코드 | 외부 크레이트(`rand` 등), 다른 파일을 불러오는 `mod 이름;`, 2024 에디션 전용 문법 |
| 크기 | 실행 파일이 아니라 오브젝트 파일 크기 |
| 실행 시간 측정 | `fn main`이 있어야 하고, 종료 코드가 0이 아니면(패닉 등) 재지 않습니다 |

## 설치와 탐지

[rustup](https://rustup.rs/)으로 설치하는 것을 권장합니다. 서버는 아래 순서로 `rustc`를 찾고, 처음 찾은 것을 씁니다.

1. 환경 변수 `OPTVIS_RUSTC`에 적은 경로
2. PATH의 `rustc`
3. rustup의 기본 설치 위치: macOS/Linux는 `~/.cargo/bin/rustc`, Windows는 `%USERPROFILE%\.cargo\bin\rustc.exe`
4. (Windows만) MSYS2 UCRT64: `C:\msys64\ucrt64\bin\rustc.exe`

3번이 있어서, rustup이 셸 설정 파일로 PATH에 넣은 `~/.cargo/bin`이 서버의 PATH에 없어도 찾습니다.
찾은 결과는 서버를 시작할 때 로그로 남습니다.

```
컴파일러 'rustc'(rustc (LLVM)) → /Users/me/.cargo/bin/rustc
```

### Windows

Windows의 rustc는 설치 방법에 따라 실행 파일을 만드는 방식이 달라서, 실행 시간 측정에 필요한 것이 다릅니다.

| 설치 방법 | 어셈블리·크기 비교 | 실행 시간 측정 |
|---|---|---|
| rustup (기본 도구 모음 `x86_64-pc-windows-msvc`) | 혼자 됨 | Visual Studio Build Tools의 링커(`link.exe`)가 필요 |
| MSYS2 (`pacman -S mingw-w64-ucrt-x86_64-rust`) | 혼자 됨 | 혼자 됨 |

어셈블리와 크기는 링크하지 않고 만들기 때문에 링커가 없어도 됩니다. 링커가 없으면 실행 시간 자리에 `⏱ 실행 불가`가 뜨고,
배지에 마우스를 올리면 rustc가 남긴 링커 에러를 볼 수 있습니다. 두 가지가 모두 설치되어 있으면 위 순서대로 rustup 쪽을 씁니다.

## 코드를 어떻게 컴파일하나요

Rust는 C와 달리 크레이트 종류(프로그램인지 라이브러리인지)에 따라 결과가 크게 달라서, 코드를 보고 종류를 고릅니다.

| 코드 | 컴파일 방식 | 어셈블리에 나오는 것 |
|---|---|---|
| `fn main`이 있음 | 프로그램(`--crate-type=bin`) | `main`에서 실제로 쓰이는 코드 |
| `fn main`이 없음 | 라이브러리(`--crate-type=lib`) | `pub` 함수와, 그 함수가 쓰는 코드 |

반대로 컴파일하면 문제가 생깁니다. `fn main`이 없는 코드를 프로그램으로 컴파일하면 "main 함수가 없다"는 에러(E0601)가 나고,
`fn main`이 있는 코드를 라이브러리로 컴파일하면 `main`이 아무도 쓰지 않는 비공개 함수가 되어 어셈블리가 통째로 빕니다.

`fn main`은 주석을 지운 코드에서 글자로 찾습니다. 문법을 해석하지 않으므로 틀릴 수 있지만, 틀려도 결과는 맞게 나옵니다.

- **없는데 있다고 본 경우**: `impl A { fn main(&self) {} }` 같은 메서드나 모듈 안의 `fn main`. rustc가 E0601을 내면 서버가
  라이브러리로 바꿔서 다시 컴파일합니다.
- **있는데 없다고 본 경우**: 매크로가 만드는 `main`. 라이브러리로 컴파일되어 어셈블리가 비고, 노란색 안내 문구가 뜹니다.

### 라이브러리로 컴파일할 때 어셈블리에 나오지 않는 함수

rustc는 라이브러리에서 아래 함수들의 기계어를 만들지 않습니다. 코드가 틀린 것이 아니라 rustc의 정상 동작입니다.

| 함수 | 나오지 않는 이유 | 보이게 하려면 |
|---|---|---|
| `pub`이 없는 함수 | 아무도 부르지 않는 함수라서 | `pub fn`으로 바꾸거나 `pub` 함수에서 부르기 |
| 제네릭 함수 (`pub fn id<T>(x: T) -> T`) | 어떤 타입으로 쓸지 정해져야 만들 수 있어서 | `pub fn id_i32(x: i32) -> i32 { id(x) }`처럼 타입을 정해 부르기 |
| `#[inline]`이 붙은 함수 | 쓰는 쪽에서 만들도록 미뤄서 | `#[inline]`을 지우기 |

어셈블리에 함수가 하나도 없으면 이 내용을 노란색 안내 문구로 보여줍니다.
`fn main`이 있는 코드로 바꿔서 `main`에서 부르는 방법도 있습니다.

## 명령줄과 고른 이유

모든 명령에 아래 옵션이 붙습니다.

```
rustc --edition=2021 -C symbol-mangling-version=v0 -C codegen-units=1 -C opt-level={레벨}
```

| 결정 | 내용 | 이유 |
|---|---|---|
| 에디션 | 2021 고정 | 지정하지 않으면 2015가 됩니다. `cargo new`의 기본값인 2024는 인터넷에서 흔히 보는 `#[no_mangle]`을 에러로 처리합니다. 대신 2024 전용 문법인 `if let ... && ...`은 쓸 수 없습니다 |
| 심볼 이름 | `symbol-mangling-version=v0` | 기본값이 rustc 버전마다 달라서 어디서든 같은 형식이 나오도록 고정합니다. 예전 형식(`legacy`)은 안정판 rustc에서 지정할 수 없습니다 |
| 코드 생성 단위 | `codegen-units=1` | 실행 시간을 재는 프로그램도 화면의 어셈블리와 같은 방식으로 만듭니다 |
| 오버플로 검사 | rustc 기본값 그대로 (`0`에서만 켜짐) | `cargo build`(`0`)와 `cargo build --release`(`3`)에서 보는 동작과 같게 둡니다. 그래서 `0`과 `1` 사이의 차이에는 검사가 빠진 것도 섞여 있습니다 |
| 어셈블리와 오브젝트 | `--emit=asm=out.s,obj=out.o`로 한 번에 | 따로 두 번 실행할 때보다 40%쯤 빠르고(`HashMap`을 쓰는 17줄 프로그램 6개 레벨 기준 3.96초 → 2.42초), 어셈블리와 크기가 같은 컴파일의 결과가 됩니다 |
| 라이브러리의 작은 `pub fn` | `-C incremental` 추가 | rustc는 작은 `pub fn`을 쓰는 쪽에서 인라인하려고 미뤄서 레벨 `1`부터 어셈블리에서 지웁니다. 증분 빌드에서는 이 판단을 하지 않아서 함수가 남습니다. 공식 동작이 아니라서 백엔드 테스트가 실제 rustc로 확인합니다 |
| 비공개 함수 | `-C link-dead-code`를 쓰지 않음 | 쓰면 비공개 함수도 보이지만 인라인되고 남은 제네릭 코드까지 전부 남아서, `pub` 함수와 반복자로 쓴 코드의 `opt-level=2` 어셈블리가 34줄에서 183줄로, 오브젝트 파일이 696B에서 3,264B로 늘어나 비교가 왜곡됩니다 |

`-C incremental`을 쓰면 어셈블리의 `.file` 줄에 들어가는 이름이 레벨마다 달라질 수 있습니다. 코드가 아니라 이름이므로
화면의 diff는 이 줄을 같은 줄로 봅니다. 화면의 기본값인 "지시어 숨기기"를 켜 두면 이 줄은 아예 보이지 않습니다.

실행 파일은 코드와 상관없이 항상 프로그램으로 만듭니다(`-o out.exe`). `fn main`이 없으면 이 단계만 실패하고 `⏱ 실행 불가`로 표시됩니다.

## 화면에서 C/C++과 다른 점

- **레벨이 여섯 개**입니다. 열 제목과 비교 기준 버튼이 `opt-level=0` ~ `opt-level=z`로 나옵니다. 기본 비교 기준은 `opt-level=0`입니다.
- **`opt-level=0`의 어셈블리가 훨씬 깁니다.** 반복자, `Option`, `Vec` 같은 표준 라이브러리의 제네릭 코드가 내 코드 안에 만들어지고
  인라인되지 않기 때문입니다. `HashMap`을 쓰는 17줄 프로그램도 약 1만 7천 줄이 나옵니다. "지시어 숨기기"(기본값)를 켜 두면 예외 처리 표와
  지시어가 빠져서 30%쯤 줄어듭니다(rustc 1.98.1에서 15,839줄 → 11,180줄). 줄이 아주 많으면 바뀐 줄 강조를 건너뛰는데,
  이럴 때는 비교 기준을 `opt-level=1`이나 `2`로 바꾸면 됩니다.
- **함수 이름이 복잡합니다.** `__RNvCslneCz6SEpaJ_5input8sum_loop`처럼 맹글링된 이름이 나옵니다. 숫자는 바로 뒤에 오는 이름의
  글자 수라서, `5input`은 크레이트 이름 `input`(입력 파일 이름), `8sum_loop`는 함수 이름 `sum_loop`입니다. 이름을 읽는 규칙은
  [rustc 문서의 v0 맹글링](https://doc.rust-lang.org/rustc/symbol-mangling/v0.html)에 있습니다.
- **최적화 기록이 나오지 않습니다.** C/C++에서는 열마다 컴파일러가 남긴 기록(무슨 최적화를 했고 무엇을 못 했는지)이 나오지만
  Rust에는 없습니다. rustc의 `-C remark=all`은 위치를 얻으려면 디버그 정보를 켜야 해서 어셈블리와 크기가 달라지고,
  나오는 기록도 대부분 표준 라이브러리 내부의 맹글링된 이름이라 내 코드의 줄과 연결되지 않기 때문입니다.
- **실행 중 패닉은 `⏱ 실행 불가`로 표시합니다.** 오버플로 검사는 `opt-level=0`에서만 켜져 있어서, 같은 코드가 `0`에서만 패닉으로
  바로 끝날 수 있습니다. 그대로 재면 `0`이 가장 빠른 것처럼 보이므로 종료 코드가 0이 아니면 시간을 버립니다.

레벨별로 무엇이 바뀌는지는 [사용자 가이드의 예제 풀이](./user-guide.md#rust-예제로-읽어보기)와
[optimization-levels.md의 Rust 표](./optimization-levels.md#rust의-opt-level)를 보세요.

## 시간 제한

| 단계 | 제한 | 넘으면 |
|---|---|---|
| 레벨 하나 컴파일 | 30초 | 다른 레벨이 성공했으면 그 레벨만 한 번 더 컴파일. 그래도 넘거나 모든 레벨이 넘으면 "컴파일 시간 초과" |
| 실행 한 번 | 5초 | "실행 시간 초과" |

컴퓨터를 켜고 처음 컴파일할 때는 rustc와 표준 라이브러리를 디스크에서 읽느라 느립니다. 새로 만든 Windows 가상 머신에서는
첫 컴파일의 레벨 하나가 30초를 넘긴 적이 있고, 그 레벨을 다시 컴파일해서 약 42초 만에 정상 결과가 나왔습니다.
같은 조건에서도 가상 머신마다 몇 초에서 수십 초까지 차이가 컸습니다.
모든 레벨이 시간을 넘기는 코드는 여섯 레벨을 모두 기다리므로 결과가 나오기까지 약 3분이 걸립니다.

## 검증한 범위

Rust 지원을 추가한 [PR #13](https://github.com/gwangholee507/optimeter/pull/13)에서 아래 환경으로 확인했습니다 (2026-11-03).

| 환경 | 확인한 것 |
|---|---|
| macOS (Apple Silicon), rustc 1.98.1 | API와 화면 시나리오 105개 |
| GitHub Actions Windows x64, Windows 11 ARM64 (rustup으로 설치된 rustc) | 같은 시나리오 105개씩 |
| GitHub Actions Windows x64 + MSYS2 rustc | 기본 위치 탐지, 예제, 실행 시간 측정, 패닉 판정 등 7개 |
| GitHub Actions Windows x64, MSVC 링커를 지운 상태 | 어셈블리·크기 비교는 되고 실행 시간은 `⏱ 실행 불가`와 링커 메시지가 뜨는지 |
| CI (Ubuntu, macOS, Windows) | PR마다 실제 rustc로 백엔드 테스트 |

시나리오에는 아래 언어 기능을 쓴 프로그램을 여섯 레벨 모두 컴파일하고 실행하는 것도 들어 있습니다.
구조체·`impl`·트레이트, `enum`·`match`, 클로저·반복자, 제네릭·트레이트 객체, 컬렉션·문자열, `Rc`·`RefCell`, 스레드·채널,
`Result`·`?`, `unsafe`·원시 포인터, `const fn`·배열·슬라이스, 인라인 어셈블리, `u128`·실수 연산, 파일 입출력, 시간·환경 API.

확인하지 못한 것:

- 실제 Windows PC (Windows Defender가 켜진 상태의 첫 컴파일, 한국어 Windows)
- Linux 배포판 패키지로 설치한 rustc (`apt install rustc` 등). CI는 rustup의 최신 안정판을 씁니다
- 컴퓨터를 켠 직후 Mac에서의 첫 컴파일 시간
