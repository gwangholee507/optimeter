# 최적화 레벨(O0~O3) 차이점

이 프로젝트가 비교하는 clang/GCC 최적화 레벨(`-O0`, `-O1`, `-O2`, `-O3`)이 각각 무엇을 하는지 정리한 문서입니다.
C++의 clang++/g++도 같은 레벨을 그대로 씁니다. 화면의 ⓘ 툴팁에 뜨는 짧은 설명은 백엔드의 `GccStyleToolchain`에 있습니다.
Rust의 `opt-level`은 [아래](#rust의-opt-level)에 따로 정리했습니다.
실제 동작은 `CompilerService`가 `clang -S -O{n}`으로 어셈블리를 뽑아 프론트엔드에서 diff로 보여주는 방식으로 확인할 수 있습니다
([architecture.md](./architecture.md) 참고).

## O0 — 최적화 없음 (baseline)

- 이 프로젝트에서 다른 레벨과의 diff 비교 기준(baseline)으로 사용됩니다.
- 소스 코드를 거의 그대로 어셈블리로 변환. 변수는 대부분 스택에 저장되고 재사용되지 않음.
- 컴파일이 가장 빠르고, 디버깅 정보와 소스 라인이 1:1로 대응되어 디버깅용으로 적합.

## O1 — 기본 최적화

- 코드 크기와 컴파일 시간을 크게 해치지 않는 선에서 적용되는 최적화.
- 주요 패스: 죽은 코드 제거(dead code elimination), 간단한 상수 전파/폴딩, 기본적인 레지스터 할당 개선.
- 함수 인라이닝은 아주 작은 함수 정도만 제한적으로 수행.
- 루프 최적화는 거의 없음.
- O0 대비 스택에 불필요하게 저장/로드하던 값들이 레지스터로 유지되며 사라지는 경우가 많음.

## O2 — 권장 프로덕션 레벨

- O1의 모든 최적화 + 더 공격적인 패스가 추가됨.
- 함수 인라이닝 범위 확대, 제한적인 루프 언롤링, 명령어 스케줄링, 강도 감소(strength reduction, 예: 곱셈 → 시프트 변환).
- 자동 벡터화(SIMD)는 기본적으로 비활성 또는 매우 제한적(컴파일러/버전에 따라 다름).
- 코드 크기를 과도하게 늘리는 최적화는 회피 — 속도와 크기의 균형점을 지향.
- `-fomit-frame-pointer` 등 O1에는 없던 옵션이 기본 적용됨.

## O3 — 최대 속도 최적화

- O2 + 공격적인 루프 최적화를 모두 활성화.
- 자동 벡터화(auto-vectorization), 더 적극적인 루프 언롤링, 함수 인라이닝 임계값 상향.
- 실행 속도는 대체로 빨라지지만 **바이너리 크기가 커지고** 컴파일 시간도 늘어남.
- **주의**: O3가 항상 O2보다 빠른 것은 아님. 캐시 미스, I-cache 압박, 코드 팽창 등으로 오히려 느려지는 경우도 있음.
  → 그래서 이 프로젝트처럼 실제 어셈블리와 바이너리 크기를 직접 비교해보는 것이 의미가 있음.

## 요약 표

| 레벨 | 인라이닝 | 루프 최적화 | 벡터화 | 바이너리 크기 | 컴파일 시간 |
|---|---|---|---|---|---|
| O0 | 없음 | 없음 | 없음 | 기준 | 가장 빠름 |
| O1 | 아주 제한적 | 거의 없음 | 없음 | 기준과 비슷하거나 약간 감소 | 빠름 |
| O2 | 확대 | 제한적 | 제한적/없음 | 증가 가능 | 보통 |
| O3 | 최대 | 공격적(언롤링 등) | 활성화 | 가장 큼 | 가장 느림 |

## 이 프로젝트에서 확인하는 방법

1. UI에서 언어(C/C++/Rust)를 고르고 비교할 함수를 입력한 뒤 "비교하기" 클릭.
2. `O0` 컬럼을 기준으로 `O1`/`O2`/`O3` 컬럼에서 초록색으로 하이라이트된 변경 줄을 확인.
3. 일반적으로 관찰되는 패턴:
   - **O0→O1**: 불필요한 스택 로드/스토어 감소, 상수 계산이 미리 접힘(constant folding).
   - **O1→O2**: 작은 함수 호출이 인라인되고 루프 내 중복 계산이 사라짐.
   - **O2→O3**: 루프가 SIMD 명령어로 바뀌거나 언롤링되어 명령어 수는 늘지만 반복 횟수가 줄어듦.

## Rust의 opt-level

rustc는 `-C opt-level`로 레벨을 정합니다. 화면의 ⓘ 툴팁에 뜨는 짧은 설명은 백엔드의 `RustcToolchain`에 있습니다.

| 레벨 | 의미 | 함께 알아둘 점 |
|---|---|---|
| `0` | 최적화 없음 | `cargo build`의 기본값. 정수 오버플로 검사가 켜져 있어 오버플로가 나면 패닉으로 멈춤 |
| `1` | 기본 최적화 | 오버플로 검사가 빠지고 값이 조용히 되감김 |
| `2` | 대부분의 최적화 | 반복자 같은 추상화가 대부분 사라짐 |
| `3` | 최대 속도 최적화 | `cargo build --release`의 기본값. 더 공격적인 인라이닝과 루프 벡터화 |
| `s` | 크기 우선 | 실행 속도보다 코드 크기를 줄이는 쪽을 택함 |
| `z` | 크기 최우선 | `s`보다 더 줄이며 루프 벡터화도 끔 |

C/C++과 다른 점이 두 가지 있습니다.

- **`0`과 `1` 사이의 차이가 최적화만은 아닙니다.** 오버플로 검사가 함께 빠지므로 `x * x`도 `0`에서는 검사와 패닉 분기가 붙습니다.
- **`0`의 어셈블리가 훨씬 깁니다.** 반복자, `Option`, `Vec` 같은 표준 라이브러리의 제네릭 코드가 내 코드 안에 만들어지고 `0`에서는
  인라인되지 않기 때문입니다. 대신 Rust가 말하는 "비용 없는 추상화"를 가장 잘 볼 수 있습니다.

프로젝트의 Rust 예제(`(0..n).map(square).sum()`)를 Apple Silicon의 rustc 1.98.1로 컴파일한 결과입니다.

| 레벨 | 어셈블리 (지시어 숨김 / 원본) | 오브젝트 파일 |
|---|---|---|
| `0` | 286줄 / 549줄 | 7,216B |
| `1` | 93줄 / 116줄 | 1,568B |
| `2` | 18줄 / 26줄 | 592B |
| `3` | 18줄 / 26줄 | 592B |
| `s` | 47줄 / 67줄 | 1,360B |
| `z` | 29줄 / 52줄 | 1,352B |

반복문은 `1`에서 이미 합 공식으로 바뀌어 사라지고, `2`에서는 `fold`, `sum` 같은 반복자 함수까지 인라인되어 `sum_loop` 하나만 남습니다.
`s`, `z`는 반복자 함수를 지우지 않고 따로 남겨 두어서, 이 코드에서는 크기 레벨보다 `2`의 결과가 더 작습니다.
크기 레벨이 항상 가장 작은 것은 아니라는 뜻이고, 이런 차이가 직접 비교해 볼 만한 이유입니다.
레벨별 어셈블리를 하나씩 읽는 방법은 [사용자 가이드의 예제 풀이](./user-guide.md#rust-예제로-읽어보기)에 있습니다.
